# Домен проекта: субъекты и термины — данные, а не код

Каталог отвечает за то, **о ком и о чём** агент говорит: какие субъекты он
различает, какие слова считает признаком предметной области, по каким словам
отбирает новости.

Раньше это жило в коде: восемь названий в `canonical.SUBJECTS`, пять брендов в
`schemas.COMPETITOR_BRANDS`, доменные слова в `corpus` и `web`, шаблоны
заголовков — регуляркой. Следствия были предсказуемые: второй проект на другом
домене невозможен, пополнение домена — правка `src/`, а «агент переносим»
остаётся обещанием.

## Файлы

| Файл | Коммитится | Правило записи | Что внутри |
|---|---|---|---|
| `entities.yaml` | да | переписывается целиком | субъекты, термины домена, шаблоны заголовков |

## Как читать `entities.yaml`

| Поле | Значение |
|---|---|
| `subjects[].canonical` | каноническое имя — как оно пишется в утверждении |
| `subjects[].aliases` | другие написания того же имени (латиница, разговорное) |
| `subjects[].kind` | `operator` — компания; `category` — категория рынка |
| `subjects[].country` | страна, если имя без неё неоднозначно |
| `subjects[].ours` | наш бренд: коммуникация идёт от его имени |
| `subjects[].competitor` | имя чужого бренда, недопустимое в ключевом сообщении |
| `terms[].word` | словоформа домена |
| `terms[].strong` | без такого слова совпадение доменного термина считается случайным |
| `terms[].clean` | отобрана замером как не встречающаяся в чужих областях |
| `terms[].domain` | участвует во взвешивании выдачи |
| `search.strong_terms` | слова отбора новостей и трендов по теме |
| `search.strong_stems` | те же слова в виде основ |
| `patterns.operator` | текст называет оператора связи |
| `patterns.company` | заголовок называет компанию, а не банк или смартфон |

Три признака термина (`strong`, `clean`, `domain`) — не украшение. Они
отвечают на разные вопросы: «слово вообще про нашу область?» (`strong`),
«слово не встречается в чужих областях?» (`clean`), «насколько поднять
статью в выдаче?» (`domain`). Одно и то же слово может быть сильным и не
чистым: «связь» доменная, но химическая «двойная связь» тоже.

## Почему `search` дублирует термины

`search.strong_terms` и `search.strong_stems` — свой список. Его можно было
вывести из `terms`, но тогда отбор новостей расширился бы (в фильтр попали бы
все бренды и все словоформы), и это была бы не переносимость, а незамеченное
изменение поведения. Список отбора — измеренная настройка; он живёт рядом,
а не выводится.

## Гейт: ни одного имени в `src/`

`tests/test_no_entity_names.py` держит обратное свойство:

- имя субъекта из этого файла не встречается **в исполняемых литералах**
  модулей агента. Комментарии не читаются: это пояснение для человека, а не
  правило. Легальное место для примера — комментарий, а не список исключений;
- в докстрингах имён тоже нет: пример называет роль («Оператор А»), а не бренд;
- в `prompts/roles/*.md` имя допустимо только внутри раздела «Пример»;
- второй домен задаётся файлом, и код править не нужно — это проверяется
  подменой каталога в тесте.

## Второй проект на другом домене

```bash
PF_DOMAIN_DIR=project2/domain pf doctor     # что прочитано
PF_DOMAIN_DIR=project2/domain make demo     # прогон на другом домене
```

Каталог задаётся настройкой `PF_DOMAIN_DIR`, а не `PF_KNOWLEDGE_DIR`: домен —
данные задачи по ссылке, а не накопленное хранилище. Набор тестов уводит
`knowledge_dir` в `tmp_path` (`D-29`), и домен, лежащий там, исчез бы во всех
проверках сразу.

## Нет словаря — ошибка, а не пустой домен

`pf.domain` бросает `DomainError`, если файла нет, YAML испорчен или в нём нет
субъектов и терминов. Пустой набор молчит: отбор статей перестаёт быть
доменным, а `make ci` остаётся зелёным. Такой отказ дороже падения, потому что
выглядит как работа.
