В прогоне `demo-v9` стратегия и фиксация решения объявляли по четыре
основания вывода, и все восемь записей вели на две строки таблицы

считала записи, отчёт складывал шаги, и один и тот же документ говорил:

```
demo/RESULT.md:19   | Подтверждённых оснований (уникальных) | 2 |
demo/RESULT.md:110  **Основания вывода: подкреплено** (проверено 8, подтверждено 8, ...)
```

Плюс две находки в том же месте:

1. `report._conclusion_status` не знал про `needs_review`: вывод, у
   которого основания ждут человека, в отчёте назывался «подкреплено»
   (`checked` при этом был 0 → «не проверялось»).
2. Правило статуса было записано дважды — в `workflow._conclusion_verdict`
   и в `report._conclusion_status` с комментарием «то же правило».

## Что сделано

| Что | Где |
|---|---|
| Ключ основания и счёт по уникальным ключам (худший вердикт побеждает) | `src/pf/ground.py`: `citation_key`, `tally_grounds`, `ground_buckets`, `GroundTally` |

| Объединение шагов вместо сложения счётчиков; честная ветка для старых журналов | `src/pf/report.py`: `_journal_tally`, `_declared_ground_keys`, `_collect_conclusion` |
| Слово «записей» там, где уникальные неизвестны; ветка «ждут проверки» | `src/pf/report.py`: `_grounds_markdown` |
| Пересборка документа из журнала | `demo/RESULT.md`, `reports/sessions/session-demo-v9.md` |
| Решение с фактами журнала | `docs/decisions.md`, D-21 |
| Канон и числа в документах | `docs/canon.py` (489), `README.md`, `docs/DESCRIPTION.md` |

Три случая в отчёте различаются явно:

1. журнал называет ключи оснований → счёт по объединению шагов;
2. ключей нет, отказов нет → уникальных ровно столько, сколько объявлено
   в выводе (следует из записанных вердиктов);
3. ключей нет, отказы есть → «записей», а не «оснований»: распределить
   отказы по повторным ссылкам нечем.
