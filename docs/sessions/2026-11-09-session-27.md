## 1. `T-69` — модель по роли

Причина: имя модели бралось одно на все девять ролей (`Settings.effective_model`),
хотя бриф называет «специализированные модели». Теперь `pf.roles.ROLE_TIERS`
делит роли на `extraction` (intake, collector, analyst, router, keeper),
`planning` (planner, redteam) и `synthesis` (options, strategy), а
`model_for(role, config)` выбирает имя из `PF_ROLE_MODEL_*`.

- **Модель едет с вызовом.** `LLMClient.complete(system, user, *, model="")`;
  пусто — модель по умолчанию. `Workflow._call_role` передаёт выбранную:
  клиент остаётся без состояния, и разные роли не перетирают модель.
- **Обратная совместимость.** Прямые `.complete(system, user)` (bench, lexicon,
  translate, тесты клиента) не меняются; четырём фейкам, идущим через
  `_call_role`, добавлен `model: str = ""` — логика ответа та же.
- **Умолчание — одна модель.** Демонстрация не требует трёх скачанных
  моделей, `make doctor` и живые тесты не меняются; экономия включается
  настройкой (`D-57`).

## 2. `T-62` — расчёт даёт система

Красный прогон: `-k aggregate_anchor` → **1 failed** (`notes == ()` там, где
ожидалось расхождение).

Агрегат и его первая строка делят якорь `[… #row0]`
(`analysis.summarize_series` переносит `row` первого наблюдения). Сверка чисел
плана принимала число из **любого** расчёта с этим якорем — и «среднее 87»
проходило по строке, хотя код посчитал 84,5. Это арифметика модели под видом
готового расчёта.

- `_Calculation` несёт `is_aggregate`; у агрегата показатель — полное имя со
  сводкой, а не строка источника.
- `_wants_aggregate(text)` («средн», «медиан», «размах») сужает подтверждение
  до расчётов-сводок: значение строки не подтверждает среднее (`D-58`).
- Правильная ссылка на агрегат (84,5) проходит; число вне расчётов —
  `no_calculation`; регресс оснований `-k aggregate_by_name` зелёный.
