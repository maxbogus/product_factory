# T-02 — Полюса вариантов проверяет схема

**Фаза:** 1 · **SP:** 2 · **RICE:** 7.2 · **Статус:** ✅

## Проблема

Честный набор вариантов содержит оба полюса: «ничего не менять» и
«направление не работает». Проверки не было: `Variants` требовал только
«не меньше трёх» и «названия различаются», а `keep_current_marker` и
`close_direction_marker` оставались свободными строками.

Хуже — eval-кейсы `D-05` и `D-06`, которые это правило описывают, **не могли
упасть**. Обработчик брал набор «А/Б/В» без полюсов, видел пустой маркер и
возвращал ровно ту строку, которую кейс искал в `must_contain`:

```
D-05 handler -> 'Закрыть направление'   # при любом поведении схемы
D-06 handler -> 'Оставить как есть'
D-09 handler -> 'пробел: Данных по причинам оттока…'
```

## Данные: маркеры уже врали

Аудит 25 наборов вариантов с `results.options`:

| Что | Сколько |
|---|---|
| Оба полюса в названиях вариантов | 22 из 25 |
| Маркер «Закрыть направление» при отсутствии такого варианта | 2 из 25 |
| Оба маркера пустые, полюса в вариантах есть | 1 из 25 |

Прогон `qwen3-8b-220435-1` отклоняется схемой и по другой причине — у первого
варианта пустые `objections` (`variants.0.objections`); к полюсам это
отношения не имеет, отказ был и до `T-02`. Проба «прогнать сохранённые
наборы через новую схему» даёт 22 принятых из 25, то есть 2 отказа по полюсам
и 1 по возражениям.

Заявление в `docs/HANDOFF.md` («все сохранённые прогоны заполняли оба
маркера») было неверным — исправлено в этой же задаче. Вывод: проверять надо
варианты, а маркеры выводить из них.

## Что сделано

1. **`src/pf/schemas.py`** — константы формулировок (`KEEP_CURRENT_TITLES`,
   `CLOSE_DIRECTION_TITLES`), `pole_of(title)` с нормализацией (регистр, ё,
   кавычки, краевая пунктуация) и защитой от отрицания («не закрывать
   направление» — не полюс), валидатор `Variants._poles` после `_diverse`.
   Отказ называет **какой** полюс отсутствует и какие формулировки допустимы.
2. **Маркеры выводятся из набора**: получают фактическое название варианта
   («Оставить без изменений», а не каноническую строку). Объявленный маркер
   без варианта больше не спасает набор — он отклоняется.
3. **Синонимы — константы схемы, не данные** `knowledge/lexicon`: словарь
   знаний описывает лексическую близость слов внутри утверждений, его записи
   имеют статус и подтверждаются человеком. Форма ответа — контракт схемы и не
   должна зависеть от наличия файла со словарём.
4. **`src/pf/workflow.py`** — подсказка модели в `_repair_prompt` для
   отказа «нет полюса»; формулировки берутся из констант схемы, а не
   переписываются в подсказке.
5. **`src/pf/evalrun.py`** — обработчики `D-05`, `D-06`, `D-09` идут через
   схему и возвращают её текст; запасной текст обработчика **не содержит**
   искомой кейсом подстроки.
6. **`eval/cases/scenarios.jsonl`** — `D-05`/`D-06` проверяют конкретный
   отсутствующий полюс (`нет полюса «оставить как есть»`), а не широкую
   подстроку; `expected` исправлен на `REJECT` (обработчик показывает отказ
   схемы, а не ответ с нехваткой части).

## Две ловушки, найденные красными прогонами

1. Запасной текст обработчика содержал искомую подстроку — кейс оставался
   зелёным при выключенной проверке. Поймано контрольной пробой
   (подмена `pole_of`), исправлено.
2. Общий текст отказа перечисляет **оба** полюса, поэтому широкая подстрока
   «оставить как есть» совпадала и в отказе из-за другого полюса. Кейсы
   теперь проверяют конкретную фразу.

Обе ловушки закреплены тестом `test_cases_d05_d06_go_red_without_pole_check`:
если проверка полюсов исчезнет, кейсы обязаны покраснеть.

## Цена строгости

2 из 25 исторических наборов полюса не имели (8 %): такой шаг отклоняется и
повторяется — `Workflow._ask` даёт 3 попытки и передаёт модели текст ошибки с
допустимыми формулировками. Демонстрационный прогон `demo-v9` полюса
содержит.

## Ограничение

Отрицание распознаётся только прямо перед формулировкой. «Нельзя всерьёз
закрыть направление» полюсом останется: разбор таких конструкций не
делается, и это записано в docstring `_contains_without_negation`.
