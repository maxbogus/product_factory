# Стратег Фабрики продуктов

ИИ-агент, который помогает руководителю цифрового продукта пройти путь от
размытого запроса до обоснованной продуктовой и коммуникационной стратегии —
и не бросает его после того, как решение принято.

```
запрос  →  разбор источников  →  варианты  →  стратегия  →  обязательства
                        ↑                                        │
                        └────────────  новые данные  ←───────────┘
```

## Что это

Агент — это **папка с инструкциями, знаниями и инструментами**. Он не
работает как «чёрный ящик»: каждое его действие записано в журнал, у каждого
утверждения есть основание, а отсутствие данных он называет прямо.

Главное отличие от обычного чата с ИИ:

| Обычный чат | Этот агент |
|---|---|
| Отвечает текстом | Проходит рабочий процесс по фазам |
| Факты часто выдуманы | Факт без дословной цитаты **отбрасывается** |
| Не помнит, что делал | Журнал шагов на диске, append-only |
| Нельзя остановить и продолжить | `pf resume` продолжает с сохранённого места |
| Неизвестно, сколько стоило | `pf cost` показывает расход по ролям |

## Быстрый старт

Требования: **Python 3.11+**, **Ollama** с локальной моделью. Ни ключей,
ни внешних сервисов не нужно.

```bash
# 1. Установить зависимости
make setup

# 2. Скачать модель (5.2 ГБ)
ollama pull qwen3:8b

# 3. Проверить, что всё живо
make doctor

# 4. Поставить задачу
pf run "Почему падает удержание у мобильного тарифа и что с этим делать?"
```

Если `pf` недоступен после `make setup`, используйте `python -m pf.cli ...`.

## Команды

| Команда | Что делает |
|---|---|
| `pf run "вопрос"` | Поставить задачу и провести работу до стратегии |
| `pf resume` | Продолжить сохранённую сессию с того же места |
| `pf answer "текст"` | Ответить на вопрос, который задал агент |
| `pf stop` | Остановить сессию |
| `pf log` | Показать журнал шагов с основаниями и стоимостью |
| `pf cost` | Показать расход: по итогу и по ролям |
| `pf sources "запрос"` | Показать, какие источники агент найдёт |
| `pf sessions` | Список сохранённых сессий |
| `pf eval` | Выполнить eval-сценарии и проверить правила поведения |
| `pf web "запрос"` | Найти внешние источники (требуют проверки) |
| `pf lexicon stats` | Показать лексическое покрытие и очередь незнакомых слов |
| `pf lexicon oov` | Что ждёт распознания |
| `pf lexicon enrich --dry-run` | Предложения модели по незнакомым словам (без записи) |
| `pf lexicon approve <слово>` | Подтвердить запись словаря (только после этого она участвует в проверке) |

## Как устроен

### Четыре слоя знаний (раздельно, как требуется)

| Слой | Где | Что внутри |
|---|---|---|
| Постоянные инструкции | `prompts/roles/*.md` | Правила работы каждой из девяти ролей |
| Методические знания | `methods/*.md` | Методики: факт/гипотеза, варианты, стратегия, план проверки |
| Материалы проекта | `project/` | Данные конкретной задачи |
| Состояние задачи | `state/`, `journal/` | Текущая фаза, результаты, журнал шагов |

### Девять ролей

`intake` (постановка задачи) → `planner` (план исследования) →
`router` (маршрутизация) → `collector` (сбор источников) → `analyst`
(разбор) → `options` (варианты) → `redteam` (критика) → `strategy`
(стратегия) → `keeper` (фиксация решения).

Каждая роль — файл промпта и схема ответа. Содержание правится без
перезапуска: кэш промптов проверяет время изменения файлов, а не имя
роли.

В инструкцию роли подставляются её методики из `methods/` — постоянные
инструкции говорят «что делать», методики «по каким правилам». Роль
получает только свои методики: подстановка всех сразу удваивала расход.

### Проверка оснований — главный механизм честности

Модель может написать связный и правдоподобный текст. Она не может
процитировать статью, которой нет. Поэтому каждое утверждение проверяется:

1. **Цитата** должна дословно встречаться в исходном тексте статьи.
2. Если цитаты нет — проверяется, что утверждение собрано из слов
   указанного абзаца (порог 80 %). Слова сравниваются по леммам и
   словарю близости: «клиенты» покрываются «абонентами».
3. **Числа сверяются с допуском** до десятой доли: «77,3» подтверждает
   «77,26». Для величин меньше единицы абсолютный допуск не включается.
4. **Точные термины не заменяются**: бренды, аббревиатуры и числа
   обязаны совпасть. Добавленное отрицание отклоняется.
5. **Источник должен быть релевантен задаче**: настоящая цитата из
   посторонней статьи основанием не является.

Незнакомое слово не снижает проверку молча: оно попадает в очередь
распознания (`knowledge/lexicon/oov.jsonl`), а `pf lexicon enrich`
предлагает понятие. В проверке участвует только подтверждённый словарь —
иначе подтверждение основания снова стало бы самооценкой модели.

Внешний источник не бывает подтверждённым: дословность проверяется по
скачанной странице, но статус — «требует проверки», и в отчёте он идёт
отдельным разделом.

Что не прошло проверку — попадает в журнал как отклонённое основание с
причиной. Это видно пользователю, а не прячется.

### Источники

Локальный снимок Википедии: 8 066 статей из 11 разделов
(`data/wiki/`, лицензия CC BY-SA 4.0, атрибуция — в `data/wiki/SOURCE.md`).
После удаления дублей по заголовку в поиск попадает 7 826 статей.

Десять разделов — технические (физика, химия, программирование), и статей
о телеком-тематике в них почти нет. Поэтому добавлен раздел `telecom` на
100 статей: операторы, тарифы, отток, роуминг. Собран поиском по запросам
скриптом `scripts/fetch_telecom.py` — он же объясняет, как снимок получен.

Поиск — TF-IDF по **леммам** (pymorphy3): словоформы запроса и словаря
сопоставимы, поэтому «мобильном тарифе» находит статью про «тариф».
Доменные термины отобраны замером по корпусу: «абонент» встречается в 5
статьях чужих разделов, а «связь» — в 1 402, и химическая «двойная связь»
прошла бы фильтр наравне с телекомом.

### Интернет: поиск и разбор страниц

Когда локальных оснований не хватает, агент выходит в интернет:

```bash
pf web "отток абонентов Мегафон" --parse
```

Поиск идёт тремя каналами, и это не украшение — выбора больше нет:
DuckDuckGo, Brave, Яндекс и публичные SearXNG-инстансы отвечают
анти-ботом или лимитом. Рабочие — **RSS-ленты** изданий (ТАСС,
Ведомости, РГ, Коммерсант) и **Bing News**; обычная веб-выдача Bing по
HTTP частично отдаёт результаты из чужого кэша, поэтому она только
запасная, и результаты фильтруются по теме.

Найденные страницы разбираются: проверяется `robots.txt`, служебная
разметка выбрасывается, HTML превращается в абзацы, пригодные для
цитирования.

**Правило не меняется:** внешний источник проходит проверку дословности,
но его статус — всегда «требует проверки». `confirmed` для внешних
источников недостижим. В журнале видно, какое основание внешнее и ждёт
человека.

Веб выключен по умолчанию (`PF_ENABLE_WEB`): демонстрация не должна
зависеть от сети.

### MCP

Инструменты MCP-сервера доступны из интерфейса:

```bash
pf mcp static-parser                      # список инструментов
pf mcp static-parser parse_url '{"url": "..."}'
```

Серверы лежат в соседнем репозитории `mcp-servers` и запускаются в своём
окружении: у них тяжёлые зависимости, несовместимые с лёгким окружением
агента. Путь задаётся переменной `PF_MCP_DIR`.

### Свои материалы и хранилище знаний

Материалы проекта — третий слой знаний: свои документы и таблицы из
каталога `project/`. Агент читает их **наравне** с корпусом: те же
идентификаторы `project/<файл>`, та же проверка дословности цитаты.
Строка таблицы становится цитатуемым абзацем, поэтому на неё можно
сослаться так же, как на абзац статьи.

```bash
pf materials                    # что загружено: вид, абзацы, хеш
pf sources "отток абонентов"   # попали ли материалы в срез источников
```

Поддерживаются `.md`, `.txt`, `.csv`, `.tsv`, `.json`, `.pdf`, `.docx`,
`.xlsx`. Для последних трёх нужен набор библиотек:

```bash
uv sync --extra documents
```

Открытые данные агент складывает в **хранилище знаний** —
`knowledge/raw/<дата>/` с манифестом: адрес источника, дата получения и
хеш содержимого. По хешу видно, изменились ли данные с момента, когда на
них опирался вывод.

Этот цикл работает — его исполняет `pf review`:

```bash
pf review --session demo-v12         # какие выводы затронуты новыми данными
pf review --session demo-v12 --json  # то же машинно
```

Пересмотр ничего не переписывает: он сравнивает записанный хеш с текущим
файлом и называет затронутые шаги и обязательства. Пометка —
«требует пересмотра», а не «вывод неверен»: хеш меняется и при
косметической правке файла. Проверяются оба корня данных — материалы
проекта (хеш в `<файл>.meta.json`) и сырые выгрузки (хеш в манифесте);
если хеш не записан, это так и называется, а не выдаётся за «не
изменилось».

```bash
make fetch-data                 # собрать открытые данные
pf knowledge                    # что скачано, откуда и какой версии
```

Манифест append-only, как журнал шагов: историю работы не переделывают.

### Расчёты по данным

Числа считает **код**, а не модель. Модуль `src/pf/analysis.py` умеет
median, mean, percentile, изменение и CAGR; русские форматы чисел
разбираются сами («11,923 млн» → `11.923`).

Каждая метрика несёт **provenance**: источник, номер строки, формулу и
входные значения. Метрика проверяется **пересчётом** по строке
источника: число нельзя «процитировать», его можно только посчитать
заново — поэтому выдуманная метрика отбрасывается так же, как
выдуманная цитата.

Изменение считается по рядам: ряд — это одна и та же величина во
времени (тот же оператор **и** тот же показатель). Складывать разные
операторы в один ряд бессмысленно.

### Отчёт по прогону

```bash
pf report                       # отчёт: числа, расход, границы замера
pf report --session demo-v9     # по конкретной сессии
pf report --json                # для машинного чтения
pf report --save                # сохранить в reports/sessions/
```

Отчёт собирается по журналу шагов, поэтому цифры воспроизводимы.
В нём есть обязательный раздел **«чего этот замер не показывает»**:
подтверждение основания — это дословное совпадение, а не смысловая
поддержка; доля подтверждённых не измеряет полноту; условные единицы —
это токены, а не деньги.

Раздел **«Вывод»** отвечает на заданный вопрос: направление, обязательства
с владельцем и условием пересмотра, план проверки — и статус оснований
самого вывода (`подкреплено` / `частично` / `неподкреплено`). Основания
вывода — `evidence` стратегии, `promise_grounding` коммуникации и `basis`
обязательств — проходят ту же проверку, что и факты: дословность цитаты и
релевантность источника задаче. Вывод без подтверждённого основания так и
называется, а не выглядит благополучно.

### Продолжение после перерыва

Состояние — обычный JSON на диске:

```bash
pf run "вопрос"      # работает до фазы, где нужен человек
pf answer "ответ"    # отвечаем
pf resume            # продолжает
```

Работа продолжается и в новом чате: состояние лежит в файле, а не в памяти
процесса.

## Модель

По умолчанию — локальная `qwen3:8b` через Ollama: без ключей и без
затрат. Модель поменьше (`qwen2.5:7b`, 4.7 ГБ) тоже работает, но
приводит цитаты реже — тогда основания проверяются по покрытию
абзацем.

**Измерено на демонстрационной задаче** (3 прогона каждая):

| Модель | Размер | Подтверждённых оснований | Время прогона |
|---|---:|---:|---:|
| `qwen2.5:7b` | 4.7 ГБ | 0, 2, 2 | ~100 с |
| `qwen3:8b` | 5.2 ГБ | **5**, 0, … | ~100–200 с |
| `mistral-nemo:12b` | 7.1 ГБ | см. `reports/bench/` | ~200–300 с |

`qwen3:8b` — лучший выбор на 8 ГБ VRAM: больше подтверждённых
оснований. Это reasoning-модель, поэтому thinking-режим выключается
явно (`PF_OLLAMA_THINK=false`) — иначе вместо JSON приходит рассуждение.

Поддерживается любой OpenAI-совместимый API:

```bash
cp .env.example .env
# в .env: PF_LLM_PROVIDER=openai, PF_LLM_BASE_URL=..., PF_LLM_API_KEY=..., PF_LLM_MODEL=...
```

Например, DeepSeek (`https://api.deepseek.com`, модель `deepseek-flash`):
прогон агента стоит **$0.005–0.03**.

## Сравнение с обычным чатом

Бриф требует измерить, насколько агент лучше обычного чата с ИИ. Это
делает `scripts/bench.py`: та же задача, та же модель, два режима — агент
и один промпт без проверки.

```bash
make bench                                    # текущая модель, 3 прогона
make bench MODELS="qwen3:8b" REPEATS=5       # другая модель
```

Измерения копятся в `reports/bench/runs.jsonl` и, если установлен
MLflow, — в его базе. Отчёт: `reports/bench/comparison-*.md`.

## A/B проверки оснований

Сравнивать «прогон против прогона» бессмысленно: на одной задаче число
подтверждённых оснований различается в разы из-за модели. Поэтому
`scripts/replay_verification.py` повторяет **проверку** на сохранённых
результатах ролей: данные одинаковые, меняется только код — и дельта
принадлежит правкам.

```bash
make replay                                  # замеренные прогоны
make replay SESSIONS="demo-v7 demo-v9"       # выбранные
uv run python scripts/replay_verification.py --json /tmp/new.json --compare /tmp/base.json
```

Шесть контрольных проб (округление числа, словоформа, смешанная
раскладка, подмена бренда, иностранная страница, добавленное отрицание)
проверяются при каждом запуске: они не зависят от журналов и ловят
регресс сразу. `state/` и `journal/` в `.gitignore`, поэтому на чистом
клоне скрипт скажет, что повторять нечего, а не покажет ноль.

## Замер семантики: нужна ли модель эмбеддингов

Проверка оснований сравнивает слова, а не смысл: дословная цитата,
поставленная не к тому утверждению, проходит (`D-19`). Прежде чем добавлять
модель эмбеддингов в зависимости, вопрос решается числами (`D-37`):
`scripts/semantic_bench.py` считает близость «утверждение — цитата» тремя
способами на размеченном наборе `eval/pairs/out_of_place.jsonl` (60 пар:
честные и «дословно, но не по месту»), калибрует порог на половине `train` и
считает полноту и точность на `test`.

```bash
make semantic-bench                          # TF-IDF — пол, без моделей
make semantic-bench METHODS="tfidf rubert sbert"   # нужны torch/transformers
```

Модели в `pyproject.toml` не входят (`D-09`): замер идёт одноразовым
окружением, чтобы `.venv` оставался один:

```bash
uv run --with torch --with transformers --with sentence-transformers \
    python scripts/semantic_bench.py --method tfidf --method rubert --method sbert
```

Гейт из четырёх критериев: точность подтверждений не падает, полнота флага
≥ 0,7, выигрыш отбора nDCG@5 ≥ +0,05, время и память в бюджете (10 % прогона,
1 ГБ). Критерий без данных называется «не измерено», а не нулём. Снимок
замера — `reports/semantic/<дата>-<методы>.json`, вердикт собирается из него в
`docs/decisions.md` (`D-37`) и сверяется тестом.


Главное измерение — **подтверждённые основания**. У обычного чата их
быть не может: их проверяет код агента дословным поиском, а не модель.
Цена агента — токены (проверка, журнал, обязательства) и время.

## Стоимость

Считается в **условных единицах**: 1 единица = 1 000 000 токенов. Это объём,
который легко перевести в деньги по тарифу модели. `pf cost` показывает
сумму и разбивку по ролям.

Полный прогон демонстрационной задачи на `qwen3:8b` (сессия `demo-v12`) —
**54 851 токен** (0.0549 единицы) и **~6 минут** на CPU. На `qwen2.5:7b` —
около **20 000 токенов** и **~100 секунд**. Разбивка по ролям —
в `pf cost`, пошаговый отчёт — в `demo/RESULT.md`.

## Ограничения

Честно о том, что агент **не** умеет:

- **В корпусе нет данных об оттоке абонентов.** Википедия и новости дают
  рыночный контекст (тарифы, конкуренция, абонентская база операторов), но
  не внутреннюю телеметрию. Агент это называет как пробел — именно так и
  должно работать.
- **Качество зависит от модели.** 7B находит 0–2 основания, `qwen3:8b` — до
  5 на той же задаче. Увеличение размера модели — первое, что стоит
  попробовать.
- **Веб-источники по умолчанию выключены** (`PF_ENABLE_WEB`). Включённый
  веб-поиск даёт источники со статусом «требует проверки», а не
  «подтверждено»: внешнее никогда не выдаётся за проверенный факт.
- **Поиск в интернете неполон.** DuckDuckGo, Brave, Яндекс и SearXNG
  отвечают анти-ботом или лимитом; работают RSS-ленты и Bing News.
- **Проверка цитат ловит пересказ, а не ложь по смыслу.** Цитата из
  настоящей статьи проходит. Поэтому проверяется ещё и релевантность
  источника задаче.
- **Разброс между прогонами велик.** На одной и той же задаче агент
  находит от 0 до 5 подтверждённых оснований: локальная модель нестабильна.
  Для честного сравнения нужен не один прогон, а несколько — поэтому
  `make bench` повторяет прогоны и считает среднее.

## Разработка

```bash
make test        # 694 теста, без обращения к модели
make test-slow   # живые тесты с моделью
make eval        # eval-сценарии: правила поведения агента
make bench       # замеры: агент против обычного чата
make lint        # ruff
make format      # ruff format
make typecheck   # mypy --strict
make ci          # всё вместе
```

### Как ведётся работа

Развитие проекта идёт сессиями по 1–2 задачи, и это видно, а не
подразумевается:

| Что | Где |
|---|---|
| Очередь задач: фазы, оценки, критерии приёмки | `docs/TASKS.md` |
| Выбор задач на сессию по RICE | `make next-task` |
| Состояние работы на сейчас | `docs/HANDOFF.md` |
| Журнал сессий | `docs/sessions/` |
| Единственный источник чисел для документов | `docs/canon.py` |

У каждой задачи критерий приёмки — **команда, которая падает**, пока задача
не сделана; у закрытой — путь к тесту, который её держит. Проверяют это
гейты `make tasks-check` и `make docs-check` (оба входят в `make ci`).

Тесты делятся на две группы: детерминированные (проверка оснований, схем,
состояния — идут без модели) и те, что бьют по живой модели (`make test-slow`).
