# Стратег Фабрики продуктов — карта проекта

> Этот файл — единая точка входа для ИИ-агента, работающего с репозиторием.

## Что это

ИИ-агент для руководителя цифрового продукта: от размытого запроса до
продуктовой и коммуникационной стратегии с проверяемыми основаниями, плюс
работа после решения (обязательства и пересмотр).

## Архитектура

```

  config.py      настройки из окружения (.env), без секретов в коде

  sources.py     отбор статей, нарезка на цитатуемые абзацы, ссылки
  materials.py   свои документы и таблицы: чтение, строки, метаданные
  analysis.py    расчёты по данным: median, mean, изменение, CAGR
  report.py      отчёт по прогону: числа, расход, границы замера
  knowledge_store.py хранилище знаний: сырые выгрузки и манифест
  ground.py      ПРОВЕРКА ОСНОВАНИЙ: цитата должна быть дословной
  hypotheses.py  вердикт гипотезы: support/refute/unknown по основаниям
  lexical.py     лексическая близость: леммы, точные термины, числа, распознавание
  synonyms.py    словарь близости: группы взаимозаменяемых понятий
  lexicon.py     словарь из файла и очередь распознания незнакомых слов
  llm.py         клиент модели (Ollama / OpenAI-совместимый), ретраи
  schemas.py     схемы ответа: ограничения на форму и содержание
  roles.py       реестр ролей: промпт + схема
  knowledge.py   слой знаний: методы и скилы, подставляемые в роли
  workflow.py    конечный автомат: фазы, проверка, журнал, хуки
  hooks.py       хуки: действия по событиям (правила из hooks/*.yaml)
  web.py         внешние источники: поиск в интернете и статус «требует проверки»
  webfetch.py   разбор найденной страницы: robots.txt, HTML → абзацы
  mcp.py         клиент MCP: подключение к внешним инструментам
  tracking.py    трекинг измерений: MLflow + JSONL (накопитель прогонов)
  bench.py       замеры: агент против обычного чата
  subagents.py   субагент fact-check: перепроверка оснований
  evalrun.py     исполнитель eval-сценариев
  journal.py     append-only журнал шагов, учёт стоимости
```

## Четыре слоя знаний (раздельно, как требует бриф)

| Слой | Путь | Что правится |
|---|---|---|
| Постоянные инструкции | `prompts/roles/*.md` | Поведение каждой роли |
| Методические знания | `methods/*.md` | Методики работы |
| Материалы проекта | `project/` | Данные задачи |
| Словарь близости | `knowledge/lexicon/` | Синонимы и очередь распознания слов |
| Состояние задачи | `state/`, `journal/` | Ход работы (не коммитится) |

## Фазы рабочего процесса

```
INTAKE → PLANNING → ROUTING → COLLECTING → ANALYZING → OPTIONS → REDTEAM → STRATEGY → KEEPER → DONE
```

Роли: `intake`, `planner`, `router`, `collector`, `analyst`, `options`,
`redteam`, `strategy`, `keeper`.

У каждой фазы есть роль — это проверяется тестом: фаза без роли молча
ничего не делает.

## Ключевые файлы

- `src/pf/ground.py` — механизм честности. Правится только вместе с тестами
  в `tests/test_ground.py`.
- `src/pf/lexical.py` — лексическая близость: леммы, точные термины,
  числа с допуском, распознавание слов. Тесты — `tests/test_lexical.py`.
- `src/pf/lexicon.py` — словарь из файла и очередь распознания. Проверка
  оснований читает только `approved`; тесты — `tests/test_lexicon.py`.
- `src/pf/hypotheses.py` — правило вердикта гипотезы. `verdict_of` читает
  **подтверждённые** основания; направление и предмет — из `pf.lexical`.
  Правится вместе с `tests/test_hypotheses.py` (блок `-k verdict`).
- `src/pf/materials.py` — `scan_materials`: два корня (`project/` и
  `knowledge/raw/<дата>/`), происхождение материала, отчёт о пропуске.
  Правится вместе с `tests/test_materials.py` (блок `-k knowledge_store`).
- `src/pf/schemas.py` — ограничения на ответ. Новое поле → новый тест.
- `src/pf/analysis.py` — расчёты. Ряд — одна величина во времени; без
  группировки по рядам получаются бессмысленные величины.
- `src/pf/report.py` — отчёт по прогону. Раздел «чего замер не
  показывает» обязателен.
- `src/pf/corpus.py` — `DOMAIN_TERMS` и `STRONG_DOMAIN_TERMS`: словарь
  предметной области. При смене темы агента правится здесь.
- `prompts/roles/*.md` — 9 файлов, по одному на роль.
- `docs/TASKS.md` — индекс задач: фазы, SP, RICE, критерии приёмки.
  Гейт `make tasks-check`; карточки — `docs/tasks/`.
- `docs/HANDOFF.md` — состояние работы между сессиями; журнал —
  `docs/sessions/`.
- `docs/canon.py` — единственный источник чисел, которые называют
  `README.md` и `docs/DESCRIPTION.md`. Гейт `make docs-check`.
- `tests/test_documents_consistency.py` — заявления документов против кода:
  умолчания `.env.example` против `Settings.model_fields`, единая
  инструкция для `--extra documents`, `demo/BRIEF.md` про веб, README про
  цикл пересмотра, команды из README. Гейт `make ci`.
- `docs/decisions.md` — почему всё так.
- `docs/DESCRIPTION.md` — описание работы для сдачи (обновлять вместе с кодом).
- `docs/VIDEO_SCRIPT.md` — сценарий видеозаписи.

## Gotchas

- **Длинный контекст ломает модель.** `Workflow.CONTEXT_PASSAGES = 5` — не
  увеличивать без проверки: на 9+ абзацах локальная модель начинает
  возвращать «историю диалога» вместо JSON.
- **`extract_json` терпим к обёрткам**, но не к обрезанному ответу. Если
  пришло «JSON не закрыт» — поднимите `PF_MAX_TOKENS`.
- **Проверка оснований ловит пересказ, а не ложь по смыслу.** Поэтому
  дополнительно проверяется релевантность источника (`SourceBundle.is_relevant`).
- **Числа сверяются с допуском 0,1 для величин от единицы.** «77,3»
  подтверждает «77,26», а «78,0» — нет. Для малых величин абсолютный
  допуск не включается: 0,1 — половина от 0,2 (`src/pf/lexical.py`).
- **Синонимы расширяют понимание, но не ослабляют проверку.** Точные
  термины (числа, бренды, аббревиатуры) и добавленное отрицание
  проверяются строго. Словарь — данные: `knowledge/lexicon/synonyms.yaml`.
- **Незнакомое слово не теряется.** Оно пишется в
  `knowledge/lexicon/oov.jsonl` (append-only, в `.gitignore`), а
  `pf lexicon enrich` предлагает понятие. Записи `proposed` в проверке
  не участвуют — подтверждает человек.
- **Внешний источник не бывает подтверждённым.** Цитата проверяется по
  скачанной странице, но статус — «требует проверки». Такие основания
  идут в отчёт отдельным разделом, а не в «Отклонённые».
- **Лимит ответа говорится модели заранее.** Иначе она пишет длинный
  JSON и получает обрезок; ограничения задачи передаются всем ролям
  (`_prompt_extras`).
- **Ollama режет промпт по `num_ctx`.** Раньше окно не задавалось, Ollama
  брал своё (4096), и на сохранённых журналах 56 шагов упирались ровно в
  4096 токенов промпта: начало контекста отбрасывалось молча. Теперь окно
  передаётся явно (`PF_OLLAMA_NUM_CTX`, по умолчанию 12288 — выбрано
  замером), а признак обрезки пишется в `detail["context"]` шага и в отчёт.
  На карте меньше 8 ГБ верните 8192: при 8192 `analyst` и `strategy` снова
  упрутся, зато KV-кэш вдвое меньше (`docs/decisions.md`, D-20).
- **Числа плана и обязательств сверяются с расчётами, а не с основой слова.**
  `Workflow._check_plan_numbers` берёт из плана и обязательств только
  величины с единицей (%, п.п., млн, руб.) и требует расчёт **того же**
  показателя; сроки («3 месяца») величиной не считаются. Показатель
  расчёта берётся из строки `#rowN` (`sources.indicator_of_citation`), а не
  из имени метрики: имя — заголовок материала. Замечания попадают в
  `rejected_details`, но подсказку модели не запускают.
- **Правило основ одно.** `pf.lexical.stems` и `pf.lexical.significant_words`;
  `sources._stems` и `Workflow._stems` делегируют туда. Своя копия регэкспа
  уже пропускала подмену показателя по слову из скобок.
- **Строка таблицы отбирается по своим полям, а не по длине текста.**
  `sources._row_score`: показатель ×2, субъект ×1, прочее содержание ×0.5;
  провенанс (`источник`, `url`) из оценки исключён — иначе порядок строк
  задаёт длина URL. Доменный добор — только для строки, чей показатель
  называет объект отрасли, и с фиксированным баллом. Ничьи разрешает
  порядок источника.
- **Критерий приёмки из индекса должен выбирать все тесты задачи.**
  `-k numbers` не выбирает `test_..._number_...`: одно слово и его
  множественное число — разные подстроки. Красный прогон обязан показать
  «5 failed», а не «1 selected».
- **Ответ не обязан влезать в окно — это ошибка настроек.**
  `PF_MAX_TOKENS >= PF_OLLAMA_NUM_CTX` роняет создание настроек: иначе
  обрезка гарантирована, а выглядит как «модель ответила».
- **Вывод проверяется как факт.** `Workflow._sources_of` собирает ссылки из
  `product.evidence`, `communication.promise_grounding` и
  `commitments[].basis`; статус оснований вывода пишется в журнал шага
  (`detail["conclusion_check"]`). Гейт `conclusion-evidence-is-grounded`
  покраснеет, если проверка снова начнёт смотреть только в факты.
- **Основания вывода считаются по уникальным строкам источника.**
  `pf.ground.tally_grounds` схлопывает ссылки на один якорь и берёт худший
  вердикт: повтор подтверждённой цитаты не перекрывает отказ по той же
  строке. Шаг пишет ключи в `conclusion_check["grounds"]`, а
  `report._collect_conclusion` объединяет стратегию и решение, а не
  складывает их счётчики. Старый журнал без ключей при наличии отказов
  называется «записей» — распределить отказы по повторам нечем
  (`docs/decisions.md`, D-21).
- **Замер проверки воспроизводится харнессом.** `make replay` повторяет
  проверку на сохранённых результатах ролей (данные те же, меняется только
  код) и гоняет шесть контрольных проб; снимок (`--json`) сравнивается с
  прежним (`--compare`) по вердиктам, а не по счётчикам. Харнесс выключает
  очередь распознания на время замера: реплей не должен оставлять следов.
- **Документ демонстрации обязан отвечать на вопрос.** Раздел «Вывод»
  собирается из журнала (`pf.report.conclusion_markdown`), а не пишется
  руками: иначе он разойдётся с прогоном. `make demo-doc SESSION=...`.
- **Тесты не пишут в `state/` и `journal/`.** Каталоги подменяются на
  `tmp_path` в `tests/test_scenarios.py`; иначе после `make test` в дереве
  остаются `session-scenario-*` файлы.
- **Пустые цитаты и пустые `source_id` не роняют шаг**, но и не считаются
  основанием: они попадают в `rejected_details`.
- **Обработчик eval-кейса не должен содержать подстроку, которую ищет кейс.**
  `D-05` возвращал «Закрыть направление» при любом поведении схемы, и кейс не
  мог упасть. Теперь текст приходит из отказа схемы, а запасной текст
  обработчика искомой подстроки не содержит. Регресс —
  `tests/test_eval_cases.py::test_cases_d05_d06_go_red_without_pole_check`.
- **Полюса вариантов проверяются по названиям, а не по маркерам.** Маркер — это
  утверждение модели о своём ответе; в двух сохранённых прогонах из 25 он стоял
  при наборе без такого варианта. Маркеры выводятся из названий
  (`Variants._poles`), формулировки — константы `src/pf/schemas.py`, а не
  данные `knowledge/lexicon` (`docs/decisions.md`, D-23).
- **Выгрузка — знание, но не основание.** `knowledge/raw/<дата>/` читается как
  материалы (`PF_INCLUDE_KNOWLEDGE_RAW`), но её основание проходит
  `ground.mark_external`: цитата проверяется дословно, а статус не поднимается
  выше «требует проверки». Расчёт по строке выгрузки тоже. Копия того же файла
  в `project/` не второй источник — она называется в пропуске
  (`pf.materials.scan_materials`), а не удваивает контекст (`D-29`).
- **Пропуск материала виден.** `scan_materials` возвращает `skipped` с причиной,
  `pf materials` печатает раздел «Пропущено». Молчаливый пропуск PDF без
  `pdfplumber` выглядел как отсутствие документа в проекте.
- **Тесты не читают настоящие выгрузки.** `tests/conftest.py` уводит
  `knowledge_dir` в `tmp_path` на весь набор. Новый тест, который не подменил
  каталог, иначе зависел бы от содержимого репозитория.
- **Вердикт гипотезы ставит код.** `pf.hypotheses.verdict_of` выводит
  `supported` / `refuted` / `unknown` из **подтверждённых** оснований, а
  `Claim.verdict` из ответа модели отбрасывается валидатором. Направление и
  предмет берутся из `pf.lexical.polarity` / `topic_words` — то же правило, что
  у противоречий в фактах (`D-30`).
- **Журнал append-only.** Не переписывайте `journal/*.jsonl` — это след.
- **`state/` и `journal/` в `.gitignore`.** Результаты работы — артефакт
  прогона, а не часть поставки.
- **Thinking-режим выключен явно** (`PF_OLLAMA_THINK=false`). У `qwen3` и
  `deepseek-r1` он включён по умолчанию: модель возвращает рассуждение
  вместо JSON, и разбор падает.
- **Веб-контекст отделён от локального** блоком «ВНЕШНИЕ ИСТОЧНИКИ»:
  у внешних источников другой статус подтверждения, смешивать нельзя.
- **Bing web по HTTP отдаёт мусор из чэша.** Рабочие каналы — RSS-ленты
  и Bing News; веб-выдача только запасная и фильтруется по теме.
- **MCP-серверы требуют `mcp==1.28.0`** (на 2.x декораторы `@app.list_tools`
  убраны) и живут в своём окружении; путь — `PF_MCP_DIR`.
- **Перевод не бывает основанием.** `pf.translate` кладёт перевод рядом с
  оригиналом, но цитата сверяется с источником: дословность — по оригиналу,
  для русской цитаты — по переводу, числа — **всегда** по оригиналу. Статус не
  поднимается выше «требует проверки»: `SupportStatus` не расширяется,
  `mark_external` не ослабляется (`docs/decisions.md`, D-27).
- **Кэш переводов обязателен.** Без него `make test` и `make replay` ходили бы
  в модель, и прогон перестал бы повторяться. Ключ — хеш **исходного** текста;
  числа сверяются и при чтении кэша, а непригодный перевод в кэш не пишется
  (D-28).
- **Требование языка одно на все роли.** Оно живёт в
  `Workflow._prompt_extras`, а не в девяти промптах: пока контекст был русским,
  его отсутствие было незаметно, а на английском материале модель отвечала
  по-английски — JSON с русскими ключами и английскими значениями.
- **Английский заголовок не проходит `_matches_terms`.** Фильтр в
  `pf.web.search_web` считает основы русских слов, поэтому английский канал
  идёт отдельной командой, а не в общем списке (D-26).


## Как ведётся работа

Работа идёт сессиями по 1–2 задачи. Порядок:

1. `docs/HANDOFF.md` — где остановились и что дальше.
2. `make next-task` — 1–2 задачи с наибольшим RICE из `docs/TASKS.md`.
3. Взять карточку `docs/tasks/<ID>.md` (для задач от 3 SP), статус в
   индексе → `🔄`.
4. **Сначала падающий тест**: критерий приёмки из индекса обязан краснеть
   до работы.
5. `make ci` зелёный → статус `✅`, в карточке `**Доказательство:**` с
   путём к тесту, который это держит.
6. `docs/sessions/<дата>-session-N.md`, обновить `docs/HANDOFF.md`,
   записать шаг в `~/.cline/memory/ml-sessions.jsonl`, коммит.

Числа, которые называют документы, живут в `docs/canon.py`. Меняете число в
коде — сначала `make canon` (он сверит с деревом), потом документы;
`make docs-check` не даст им разойтись.

## Проверка перед коммитом

```bash
make ci
```
